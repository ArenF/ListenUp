# 🎵 ListenUp! — 프로젝트 구조 문서

> YouTube Data API 기반 실시간 멀티플레이어 음악 맞히기 게임 — 코드베이스 전체 구조 해석 문서

| 구분 | 내용 |
|------|------|
| 모노레포 | npm workspaces |
| 실시간 통신 | Socket.IO |
| 프론트엔드 | Svelte 5 |
| 백엔드 | Node.js + Express |
| 음원 | YouTube Data API v3 |
| 언어 | TypeScript |

**ListenUp!** 은 로그인 없이 **방 코드**만으로 즉시 참가하여, 짧게 재생되는 YouTube 음원을 듣고 곡·아티스트 이름을 가장 빨리 맞히는 웹 게임입니다. 서버는 방/게임/플레이리스트/YouTube 4개의 서비스 계층과 Socket.IO 실시간 통신으로 구성되며, 클라이언트는 게임 페이지와 플레이리스트 관리 페이지로 나뉜 Svelte SPA 입니다.

> ℹ️ 이 문서는 저장소의 실제 소스(`packages/server`, `packages/client`)를 읽어 구조·데이터 모델·이벤트 흐름을 재구성한 것입니다. 개별 기능별 개발 보고서(Markdown)를 대체하는 단일 진입 문서입니다.

## 🧩 전체 아키텍처

클라이언트와 서버는 두 개의 채널로 통신합니다. **플레이리스트 관리**는 REST(HTTP)로, **실시간 게임 플레이**는 Socket.IO 이벤트로 처리됩니다. 서버의 모든 상태(방·게임)는 메모리 내 `Map` 에 저장되는 인메모리 구조이며, 플레이리스트만 JSON 파일로 영속화됩니다.

### CLIENT · Svelte SPA
- **App.svelte** — `game ↔ playlist` 페이지 전환
- **game/** — Lobby · Room · Player · Result 컴포넌트, `gameStore` 중앙 상태
- **playlist/** — Playlist · PlaylistForm · TrackForm · TrackList
- **socket.ts** — 서버와의 단일 Socket 연결
- YouTube IFrame Player 로 음원 재생/음소거 제어

### SERVER · Node.js
- **index.ts** — Express REST + Socket.IO 서버 부트스트랩
- **services** — roomService · gameService · playlistService · youtubeService (싱글턴)
- **socket/handlers** — room · game 이벤트 핸들러 등록
- **data/playlists.json** — 유일한 영속 저장소
- 방/게임 상태는 프로세스 메모리에 보관

```
┌─────────────── Browser (Svelte) ───────────────┐
│  Game 페이지            Playlist 관리 페이지     │
│      │  Socket.IO             │  fetch / REST     │
└──────┼───────────────────────┼───────────────────┘
       │  ws: 게임 실시간       │  http: CRUD
       ▼                        ▼
┌─────────────────── Express 서버 ────────────────┐
│  socket/handlers          REST 라우트 (/api/*)   │
│      │                          │                 │
│      ▼                          ▼                 │
│  gameService   roomService   playlistService     │
│      └──────────┬───────────────┘                │
│                 ▼                                 │
│           youtubeService ──► YouTube Data API v3  │
│                 │                                 │
│           playlists.json (파일 영속)              │
└──────────────────────────────────────────────────┘
```

### 데이터 흐름 요약

| 동작 | 채널 | 경로 |
|------|------|------|
| 플레이리스트 조회/생성/수정 | REST | `GET/POST/PUT/DELETE /api/playlists` → `playlistService` → JSON 파일 |
| 방 생성·참가·설정 | Socket | `create-room / join-room` → `roomService` (메모리 Map) |
| 게임 시작 · 트랙 로드 | Socket | `start-game` → `gameService` + `youtubeService` |
| 라운드 준비·재생 동기화 | Socket | `prepare-round / player-ready / round-started` |
| 정답 제출·채점 | Socket | `submit-answer` → `gameService.submitAnswer` |

## ⚙️ 서버 진입점 — `index.ts`

Express 앱과 HTTP 서버를 만들고 그 위에 Socket.IO 서버를 올립니다. 세 가지 책임을 가집니다:

1. **REST 라우트 등록** — 플레이리스트 CRUD, 트랙 추가/삭제, YouTube 트랙 조회, 테스트/디버그 엔드포인트
2. **소켓 연결 수립** — 연결마다 `registerRoomHandlers` · `registerGameHandlers` 호출
3. **부트스트랩** — `validateEnvYouTube()` → `playlistService.initialize()` → `httpServer.listen(3000)`

```ts
io.on("connection", (socket) => {
  registerRoomHandlers(io, socket);  // 방 관리 이벤트
  registerGameHandlers(io, socket);  // 게임 진행 이벤트
  socket.on("disconnect", () => { /* 방 자동 이탈 처리 */ });
});
```

> ℹ️ Socket.IO 는 `websocket` 우선, 실패 시 `polling` 폴백. CORS origin 은 `FRONTEND_URL`(기본 `:5173`)로 제한됩니다.

## 🧠 서비스 계층 (싱글턴)

모든 서비스는 파일 하단에서 인스턴스를 하나 생성해 `export` 하는 싱글턴입니다. 상태는 인스턴스 내부 `Map`/`Set` 에 담깁니다.

### roomService — 방 생명주기

| 메서드 | 역할 |
|--------|------|
| `createRoom()` | 6자리 대문자 코드(nanoid) 생성, 호스트 등록, 초기 `GameState` 구성 |
| `joinRoom()` | 정원·중복 닉네임·게임중 여부 검증 후 참가 |
| `leaveRoom()` | 이탈 처리 · 빈 방 삭제 · **방장 이탈 시 다음 플레이어에게 방장 위임** |
| `updateSettings()` | 방장만, 게임 중이 아닐 때 설정 변경 |

### gameService — 게임 로직의 핵심

| 메서드 | 역할 |
|--------|------|
| `startGame()` | 게임 상태 초기화, 플레이리스트 라운드 수 설정, 점수/스트릭 0으로 |
| `setTracks()` / `prepareNextRound()` | 전체 트랙 저장 후 다음 라운드용 트랙을 랜덤 선택, 준비 대기 상태로 전환 |
| `markPlayerReady()` / `isAllPlayersReady()` | 플레이어별 트랙 로딩 완료 집계 → 전원 준비 확인 |
| `activatePreparedRound()` | 준비된 트랙을 현재 트랙으로 승격, 라운드 번호 증가, 타이머 시작 |
| `submitAnswer()` | 정답 검증 → 시간 기반 점수 + 스트릭 보너스 계산 → 누적 |
| `endRound()` / `endGame()` | 라운드 결과 집계 · 최종 순위/우승자 산출 및 히스토리 저장 |

### playlistService — 파일 영속 CRUD

서버 시작 시 `initialize()` 로 JSON 을 메모리에 로드하고, 변경 시마다 `savePlaylists()` 로 파일에 기록합니다. 저장 실패 시 **메모리 상태를 롤백**하는 트랜잭션 패턴을 사용합니다. 이름 중복·트랙 중복을 검증합니다.

### youtubeService — 외부 API + 캐시

YouTube Data API v3 `/videos` 엔드포인트로 `snippet + contentDetails` 를 조회합니다.

- **ISO 8601 길이 파싱** (`PT3M45S → 225초`) 후, 곡 **중간 30초** 를 미리듣기 구간으로 계산
- **node-cache** 24시간 TTL — 정렬된 videoId 조합을 키로 캐싱
- 50개 초과 시 배치 분할, 403(할당량)·429(레이트리밋) 에러 구분 처리
- 플레이리스트의 `answers` 배열을 트랙에 매핑

## 📡 소켓 핸들러

핸들러는 서비스를 호출하고 결과를 **직렬화**해 브로드캐스트합니다. 서버 상태의 `Map`/`Set` 은 JSON 직렬화가 불가하므로 배열로 변환하는 헬퍼(`serializeRoom`, `serializeRoundResult`)를 거칩니다.

> ⚠️ **정답 은닉** — 라운드 진행 중에는 `hideTrackInfo()` 로 곡명·아티스트를 제거한 `HiddenTrack`(id·embedUrl·재생구간만)을 전송합니다. 정답은 `round-ended` 시점에만 공개됩니다.

- **room.handler.ts** — `create-room · join-room · leave-room · update-settings · disconnect` 를 처리. 참가/이탈은 방 채널(`socket.join(code)`)에 브로드캐스트되고, 연결 종료 시 소속 방에서 자동 이탈합니다.
- **game.handler.ts** — `start-game · player-ready · submit-answer · next-round · game-end` 를 처리. 방장 권한을 매 이벤트마다 `room.hostId === socket.id` 로 검증합니다. 전원 답안 제출 시 **2초 후 자동으로 라운드 종료**합니다.

## 🗂️ 핵심 타입 (`types/index.ts`)

| 타입 | 설명 |
|------|------|
| `Room` | 코드·호스트·`players: Map`·설정·`gameState` |
| `GameState` | 진행중 여부·라운드·현재/다음 트랙·답안 Map·점수/스트릭 Map·준비 플레이어 Set·트랙 목록 |
| `Player` | id·닉네임·아바타(이모지)·점수·스트릭·방장 여부 |
| `Playlist` / `PlaylistTrack` | 플레이리스트 = `{ videoId, answers[] }` 트랙 배열 + `roundCount` |
| `Track` | YouTube 조회 결과 + 재생 구간(`startSeconds~endSeconds`) + `answers[]` |
| `AnswerSubmission` | 제출자·답안·경과시간·정답여부·획득 점수 |
| `RoundResult` / `GameResult` | 라운드/게임 종료 시 집계 결과(정답자·누적 점수·우승자) |

> ℹ️ **다중 정답** — 각 트랙의 `answers` 는 배열로, 곡명·아티스트·한글표기 등 여러 정답을 허용합니다(예: 강남스타일 / PSY / 싸이).

## 🖥️ 클라이언트 컴포넌트 구조

`App.svelte` 는 상단 네비게이션과 `game ↔ playlist` 페이지 전환만 담당합니다(`$state` 기반 단순 라우팅). 각 페이지는 아래 컴포넌트들로 분할됩니다.

### game/ — 게임 플레이

```
Game.svelte        # 컨테이너: 소켓 이벤트 리스너 전부 등록 · YouTube Player 생성/제어
├─ GameLobby.svelte  # 방 생성/참가 · 닉네임 · 플레이리스트 선택
└─ GameRoom.svelte   # 방 화면 (플레이어 목록 · 진행 · 조작)
   ├─ GamePlayer.svelte  # YouTube 플레이어 · 음량 · 정답 입력
   └─ GameResult.svelte  # 최종 순위 · 우승자
```

`Game.svelte` 가 실질적인 두뇌입니다. `onMount` 에서 소켓의 모든 서버→클라이언트 이벤트(`game-started · prepare-round · round-started · round-ended · game-end` 등)를 구독하고, `gameStore` 를 갱신하며, YouTube IFrame Player 의 생성·음소거·재생·정지를 지휘합니다.

### playlist/ — 플레이리스트 관리

```
Playlist.svelte     # 컨테이너: REST(fetch)로 CRUD 호출
├─ PlaylistForm.svelte # 플레이리스트 생성/수정 폼
├─ TrackForm.svelte    # videoId + 다중 정답 입력 · YouTube 미리보기
└─ TrackList.svelte    # 트랙 목록 · 정답 편집/삭제
```

## 🗃️ 상태 관리 & 소켓

### gameStore.ts
Svelte `writable` 스토어 하나에 게임의 모든 상태(연결·방·플레이어·라운드·트랙·YouTube 플레이어·음량 등)를 담습니다. `updateGameStore(partial)` 로 부분 갱신하고, `isHost` 는 `derived` 스토어로 현재 소켓이 방장인지 계산합니다.

### socket.ts
`initSocket()` 이 `autoConnect:false` 인 단일 Socket 인스턴스를 지연 생성합니다. 개발 환경에서는 빈 URL(상대경로)로 Vite 프록시를 태우고, 프로덕션에서는 `VITE_SERVER_URL` 을 사용합니다.

## 🎮 게임 진행 흐름

ListenUp! 의 가장 특징적인 부분은 **모든 플레이어의 YouTube 트랙 로딩을 동기화**한 뒤 라운드를 동시에 시작한다는 점입니다. 준비 상태 집계로 "먼저 로드된 사람이 유리한" 불공정을 제거합니다.

| # | 방향 · 이벤트 | 단계 | 설명 |
|---|--------------|------|------|
| 1 | 방장 → 서버 · `start-game` | 게임 시작 | 서버가 플레이리스트의 videoId 들을 `youtubeService` 로 로드 → `setTracks()` → 첫 트랙 `prepareNextRound()`. 전체에 `game-started` 브로드캐스트 |
| 2 | 서버 → 전원 · `prepare-round` | 라운드 준비 요청 | 정답이 제거된 `HiddenTrack` 전송. 각 클라이언트는 YouTube Player 를 생성하고 **음소거 상태로** 로딩·일시정지 |
| 3 | 각 플레이어 → 서버 · `player-ready` | 준비 완료 집계 | 로딩이 끝난 플레이어가 준비 신호 전송. 서버는 `player-ready-status` 로 진행률(`n/total`)을 브로드캐스트 |
| 4 | 서버 → 전원 · `round-started` | 동시 재생 | **전원 준비 완료** 시 `activatePreparedRound()` 로 라운드 시작. 클라이언트는 음소거를 해제하고 재생, 타이머 시작 |
| 5 | 플레이어 → 서버 · `submit-answer` | 정답 제출 & 채점 | 서버가 정규화·유사도 기반으로 채점, 점수·스트릭 갱신 후 `score-updated` 브로드캐스트. 다른 플레이어에겐 `answer-submitted`(제출 사실만) |
| 6 | 서버 → 전원 · `round-ended` | 라운드 종료 | 전원 제출 시 2초 뒤 `endRound()`. 이 시점에 **정답 트랙 전체 정보**가 공개됨 |
| 7 | 방장 → 서버 · `next-round` / `game-end` | 다음 라운드 또는 종료 | 남은 라운드가 있으면 2단계로 돌아가고, 마지막 라운드였다면 `endGame()` 으로 최종 순위·우승자를 산출해 `game-end` 브로드캐스트 |

## 🎯 채점 · 점수 로직

### 정답 판정 (`checkAnswer`)

사용자 답과 각 정답을 **정규화**(소문자 · 공백/특수문자 제거)한 뒤 세 단계로 판정합니다. 트랙에 `answers` 배열이 있으면 우선 사용하고, 없으면 YouTube 제목으로 대체합니다.

| 단계 | 조건 |
|------|------|
| 완전 일치 | 정규화 문자열이 동일 |
| 부분 일치 | 정답이 사용자 답을 포함하고 입력이 3자 이상 |
| 유사도 | **Levenshtein 거리** 기반 유사도 `> 0.8` (80%) |

### 점수 계산 (`calculateScore`)

```
기본 점수      : 1000점 (정답 시)
시간 보너스    : max(0, (제한시간 - 경과시간) / 제한시간 × 500)
               → 즉답 +500, 마감 임박 +0
스트릭 보너스  : 2연속부터 (streak - 1) × 100점 누적
```

즉, 한 라운드 최대 획득 = `1000(기본) + 최대 500(속도) + 스트릭 보너스`. 오답 시 스트릭은 0으로 초기화됩니다.

> ℹ️ `packages/server/src/__tests__/game.test.ts` 에 Vitest 로 게임 로직 테스트가 존재합니다.

## 🚀 실행 방법

cp .env.example .env
